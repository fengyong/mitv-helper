# MiTV Helper · 产品设计方案（V1 · rev2 实测修正版）

> 代号候选：**送片员 / Drop2MiTV / 电视直送**（下文暂用「MiTV Helper」）
> 版本：2026-11-18 · 目标平台 macOS 13+

> ### ⚡ 实测修正（rev2，依据：`mitv-helper-mimo26pro/docs/PRODUCT_DESIGN_mimo.md` §3 协议级实测）
>
> mimo 分支当晚对真实电视 `192.168.31.171:2121`（SwiFTP 6.0.33，匿名登录）做了协议探测，以下**实测事实推翻本文 §7 的部分假设**，开发以本修正块为准：
>
> | 项 | 本文原假设 | 实测结论 | 影响 |
> |---|---|---|---|
> | 文件名编码 | UTF-8 + 安全命名 `MITV_xxx` | **GBK 编码原名全通**（含中文/`[]`/空格/全角标点）；UTF-8 写入成功但电视端乱码 | 改为「GBK 原名保留」，仅 emoji 等不可表示字符才最小替换并记映射 |
> | 断点续传 | REST 偏移续传 | **REST 502 不支持；APPE 追加可用且已验证** | 改为 SIZE 校验 + APPE 追加式续传；且优先级降为 P2 |
> | 目标目录 | `/MITV Helper/日期/` 归档 | **MKD 550，禁止建目录**；写入现有子目录 OK（Movies/ 已验证） | 改为智能分流：视频→`Movies/`、图片→`Pictures/`、都无→根目录 |
> | 传输引擎 | curl 子进程 | REST 不可用 + curl glob 坑（`[]` 当通配符导致上传失败） | **改为自研 Swift FTP 客户端**（PASV/STOR/APPE/SIZE/LIST） |
> | 协议模式 | 未定 | **EPSV 不支持，仅 PASV**；SIZE 可用；5.4GB 单文件无碍 | 引擎按 PASV 实现 |
> | 删除/改名 | 设计了软删除 | **DELE、RNFR/RNTO 未实测** | 引擎实现之，首连探测决定软删除还是直删 |
> | v1 范围 | 含取回下载 | mimo 版定为纯上传 | **以用户本日明确要求为准：保留多选删除/下载** |
>
> 未修订部分的其余设计（需求拆解、场景、界面、多选交互）继续有效；**软删除三层已于 2026-11-19 产品决策废弃**，见下条校准与 §7.5 校准版。

> ### 🗓 2026-11-19 校准（依据：已合并实现与 `docs/20261119_design_upload_target.md` v2）
>
> - **删除**：改直删 DELE + 强确认「永久删除，无法撤销」+ 可选「删除前先下载到本地」兜底；DELE 不支持则删除入口禁用。**软删除/回收站/撤销全部废弃**；`.MITV-Trash` 标记仅用于过滤旧版本残留。

> - **文件名**：GBK 原名保留（rev2 已定），v1 的 UTF-8 探测 + ASCII 安全命名 + 映射库未采纳，§7.1 已校准。
> - 真机未实测项（DELE/RNTO 响应文本谱等）在正文显式标注。

## 1. 需求还原：你真正想要的是什么

把你提出的想法收敛成一句话：

> **把「Mac 上的照片和视频 → 小米电视大屏上播放」这件事，从「打开 FTP 客户端、看懂目录树、手动处理文件名、盯着进度祈祷」缩短为「拖一下」。**

拆开来看，包含这些明确信号：

| 你说的 | 背后的意图 |
|---|---|
| 小米电视插 U 盘后有 FTP 的 U 盘管理功能，但有中文目录等限制 | 底层通道已经存在，但**坑要由 app 来填**，不能让用户踩 |
| 想方便地上传下载视频和图片 | 双向都要，V1 以上传为主 |
| 先不做格式转换 | 转码是 V2，V1 专注「送得到」；但架构上要给它留位置 |
| 先做 Mac 版 | 单端深耕，原生质感 |
| 方便地从照片库选图片 | 照片是高频场景，选图体验决定第一印象 |
| 从 Downloads 或指定目录选视频 | 视频来自浏览器下载 / 拷贝，路径要短 |
| FileZilla 强大但交互不友好、太工程师 | **竞品参照系**：功能做减法，体验做乘法 |
| 拖一下就行 | 拖拽是一等公民，不是隐藏技巧 |
| 能断点续传 | 大视频文件传一半断了不能重来；**这是可靠性底线** |
| 可视化状态进度 | 任何时刻都知道「传到哪了、还要多久、成没成」 |
| 设计感强、优雅简洁、Mac 原生质感 | 视觉与交互是产品的一部分，不是装饰 |

**不做的事（V1 明确出圈）：** 通用 FTP 客户端、站点管理器、双栏目录树、同步功能、格式转码、DLNA/AirPlay 投屏、Windows/iOS 版。

## 2. 调研结论

### 2.1 小米电视端：FTP「远程管理」是什么

- 入口：电视插 U 盘 → 打开自带「**高清播放器**」→ 遥控器**菜单键** →「**远程管理**」，屏幕显示形如 `ftp://192.168.x.x:2221` 的地址（部分机型/版本为 **2121**）。
- 需要电视与 Mac 在**同一局域网**；**弹窗关闭即服务停止**（这是断线的主要来源，产品必须优雅处理）。
- 通常**匿名即可登录**；Win 等客户端若禁空密码，可自设用户名密码（我们默认匿名，允许手填）。
- 该服务把**插着的 U 盘**暴露给 FTP（所以电视端播放天然走「高清播放器 → U 盘」路径，上传完立刻能看）。
- 电视端播放器用 **UTF-8** 解析文件名；部分场景下 FTP 通道创建**中文/非 ASCII 文件名会乱码或失败**——即你说的「不支持中文目录」。

### 2.2 电视能播什么（为 V2 转码储备）

- 常见容器（MP4/MKV/MOV/AVI/RMVB…）与 H.264/H.265 视频基本可播。
- 典型「播不了/没声音」原因是**音频编码授权**（DTS / Dolby AC3-EAC3 部分机型不解码 → 有画面没声音）。
- V2 的转码策略应是「**探测 → 优先 remux 转封装（视频流不动，音轨转 AAC）→ 必要时才重编码**」，快且无损画质。V1 不做，但上传时**顺带探测编码并记录**，为 V2「这个文件电视可能播不了」提示做数据准备（可选项，默认开）。

### 2.3 竞品与替代品

| 方案 | 它解决了什么 | 它没解决什么（= 我们的机会） |
|---|---|---|
| FileZilla / Cyberduck / Transmit | 通用、强大 | 站点/协议/被动模式概念多；照片库取不出原图；无队列续传的贴心处理；审美是工程师的 |
| Finder 直连 `ftp://` | 零安装 | 只读挂载（不可写）、无进度、断线易死、中文路径坑照踩 |
| AirPlay / 无线投屏类 App | 即时镜像 | 是「投屏」不是「送到电视本地」；照片视频被压缩、卡顿依赖网络；文件不落地 |
| 小米互传 / 云相册 | 跨端同步 | 要账号和云端中转，隐私与速度都打折，且不解决 U 盘场景 |
| U 盘来回拷 | 稳定 | 物理劳动，最不优雅 |

**定位空档：没有任何产品把「Mac 照片库/文件夹 → 小米电视 U 盘」做成 AirDrop 级体验。**

### 2.4 macOS 侧技术可行性（均已验证）

| 能力 | 方案 | 结论 |
|---|---|---|
| 照片库选图/选视频 | `PHPickerViewController`：系统级多选界面、**无需相册权限**；`loadFileRepresentation` 拿到**原始文件**（HEIC/MOV），临时文件需先落入 staging | ✅ 体验和系统照片 App 一致，免费获得优雅 |
| 文件/目录选择 | `NSOpenPanel`，默认定位 `~/Downloads`，记住上次目录；支持选整个文件夹（自动展开里面的视频） | ✅ |
| FTP 引擎 | 三选一（见 §6.2）：系统 curl 8.7.1（**本机已验证支持 ftp/ftps**，`-C -` 原生断点续传）／自研 Swift FTP 客户端（协议简单，~几百行）／SPM 社区库（维护一般） | ✅ 建议 V1 用 curl 起步 + 抽象接口 |
| 断点续传 | FTP `SIZE` + `REST offset` + `STOR`（或 `APPE`）；**电视服务器是否支持需实测**，不支持则降级为整文件重传 | ⚠️ M0 探测定案 |
| 局域网发现 | 电视 FTP 无 Bonjour 广播 → 上策：解析用户输入的 `ftp://ip:port`；中策：对局域网段 2121/2221/21 端口快扫自动列出候选 | ✅ |
| 队列持久化 | JSON/SQLite 存队列 + staging 缓存导出的照片原件 → 重开 app 自动恢复 | ✅ |

**本机环境备注：** macOS 13.7.8，当前只有 Command Line Tools（Swift 5.1），**需安装 Xcode 14/15 才能开发**；系统 curl 已带 FTP，可直接用于 M0 探测。

## 3. 产品定位与设计原则

**一句话定位：** 面向「家里有小米电视的 Mac 用户」的照片视频直送工具——像 AirDrop 一样简单，像原生 Mac 应用一样精致。

### 设计原则（所有决策的裁判）

1. **只做一件事**：把照片视频送到电视上。功能敢于不 做。
2. **零术语**：界面永远不出现「主机、端口、被动模式、字符集、FTP」。用户只需要知道「电视」。
3. **拖拽优先，点击其次，配置最后**：拖到窗口/拖到 Dock 图标都能传；按钮是备胎；设置只有一页。
4. **状态永远可见，失败永远可救，删除永远谨慎**：每个文件有进度、速度、剩余时间；断线自动等待重连并从断点继续；删除为直删 + 强确认（「永久删除，无法撤销」），可选「删除前先下载到本地」兜底，不弹错误对话框轰炸用户（2026-11-19 校准：软删除可撤销废弃）。
5. **原生质感**：SwiftUI + SF Symbols + 毛玻璃 + 深浅色自适应 + 克制的动画（完成时轻微弹跳）。宁可留白，不可拥挤。

## 4. 目标用户与核心场景

**用户画像**：家里有小米电视 + Mac 的普通人（比如你自己）：拍了很多照片视频在 Mac/iPhone 上，想在客厅大屏给家人看；偶尔下载了电影想推到电视播。

**四个核心场景（用户故事）**

1. **家庭相册分享**（最高频）：刚旅行回来 → 打开 app → 点「从照片选择」→ 挑 30 张照片 → 拖入/点「发送」→ 电视上「高清播放器 → U 盘」幻灯片播放。
2. **推一部下载的电影**：从 Downloads 拖 `某某电影.mkv`（812MB）到 app 窗口 → 看进度条 → 中途关了电脑，第二天打开自动从 60% 继续。
3. **管理电视 U 盘上的内容**（低频但要有）：浏览 U 盘文件 → 拖回本地下载；看完的、占空间的照片视频 → 多选勾上 → 一键删除（强确认 + 可选删除前先下载兜底）。
4. **第一次连接**：按引导在电视上打开远程管理 → 输入电视屏幕显示的地址（或自动查找）→ 3 秒完成，之后永久记住。

## 5. 功能范围（V1）

### 5.1 V1 做

| 模块 | 内容 |
|---|---|
| 连接 | 首次向导（图文教开远程管理 + 输入地址 + 自动查找候选）；记住电视；心跳检测掉线 → 自动重连；电视 IP 变了自动重新定位 |
| 选照片 | 系统照片选择器（PHPicker），多选、原图导出、包含 Live Photo 与视频 |
| 选视频 | 文件/文件夹选择器（默认 ~/Downloads、记住上次）；Finder 拖拽；Dock 图标拖拽 |
| 上传队列 | 可视化列表（缩略图/进度/速度/剩余时间）；暂停/继续/取消/重试；并发 ≤2；完成通知（系统通知 + 轻声效） |
| 断点续传 | app 重开自动恢复队列；断线自动等待重连后从断点继续（服务器支持 REST/APPE 时），否则整文件重传 |
| 文件名 | GBK 原名保留；不可表示/风险字符最小替换（规则见 §7.1 校准版）；同名比尺寸+指纹去重 |
| 目标路径 | 智能分流：视频→`Movies/`、照片→`Pictures/`、都无→根目录（2026-11-19 定案，MKD 550 禁建目录）；可指定存放位置见 `docs/20261119_design_upload_target.md` |
| 浏览与删除 | 网格浏览 U 盘文件（缩略图）；多选（⌘/⇧/悬停勾选）→ 批量下载或删除；**直删**：强确认 + 可选「删除前先下载到本地」兜底；DELE 不支持则删除禁用（见 §7.5 校准版） |
| 边缘保护 | >4GB 文件上传前提示「若 U 盘是 FAT32 将无法容纳」；上传前估算剩余空间不足时预警 |

### 5.2 V1 不做（写进「未 来」而不是砍掉）

格式转码（V2）、电视端自动打开文件（受限于电视无远程控制 API）、菜单栏迷你投递口（V1.1）、旧版回收站残留清理（V1.1，现仅浏览过滤）、iOS 版、非小米电视适配（V3 抽象传输层）。

单窗口应用，三个区域，没有第二个「主界面」：

```

│  空闲态：大拖放区（插画 + 一句话引导）            │
```

细节规则：
- 每行：缩略图（照片=原图缩略；视频=首帧；其他=SF Symbol）+ 文件名 + 原始大小 + 进度条 + 速度/剩余时间；悬停浮现操作（暂停/继续、取消、失败时「重试」+「查看原因」）。
- 完成的行停留 10 秒后收进「已完成」折叠组，不刷屏；「已完成」组可一键清空。
- 断线时顶部胶囊变黄：「电视连接不上 · 正在重试（第 3 次）」，队列自动整体暂停，不弹模态框。
- 整队完成 → 系统通知「5 张照片已送到电视 📺」+ 窗口轻微弹跳动画。

- 勾选任意一项 → 底部浮出毛玻璃操作条（已选数量/总大小 + 下载 + 删除）；清空选择自动收起。
- 点「删除」→ 确认浮层：缩略图条 +「永久删除，无法撤销」+ 可选「删除前先下载到本地」勾选 → 执行中「正在移除 2 项…」→ 完成 toast「已永久删除 2 项」（无撤销）。
- 旧版本软删除残留的 `.MITV-Trash` 目录/前缀文件由浏览过滤隐藏（不再新写回收站，无还原/清空入口）。

## 7. 关键体验问题的设计决策

### 7.1 文件名：GBK 原名保留（2026-11-19 校准，取代 UTF-8 探测 + ASCII 安全命名）

实测 GBK 原名全通（含中文/`[]`/空格/全角标点），UTF-8 写入成功但电视端乱码 → 控制通道与文件名**恒定 GBK**：
1. GBK 可表示 → 原名保留；
2. 不可表示字符（emoji 等）与文件系统风险字符 → 最小替换 "-"（去尾部空格/点），规则见 `NameCodec`；
3. 远端同名 → 比尺寸 + 前 10MB 指纹：相同文件跳过上传，不同文件改名 `原名-<md5前8>.ext`（判定不了保守改名，绝不覆盖）；
4. 目录名（智能分流 `Movies`/`Pictures`）天然 ASCII，不受影响。

`Capabilities.utf8Filenames` 探测位仅作信息上报，引擎不按它切换编码。v1 的「MITV_时间戳安全命名 + SQLite 映射库」未采纳。

### 7.2 断点续传（可靠性底线）

- 传输引擎把「任务 + 已确认字节偏移」落盘（每 2 秒）；app 崩溃/重启后队列原样恢复。
- 断线（常见于电视端关掉远程管理弹窗、U 盘被拔）：指数退避自动重连（5s/15s/30s…最长 5 分钟），期间 UI 只变黄不报错；重连成功后 `SIZE` 远端 → `REST offset` 续传。
- 服务器不支持 REST/APPE（M0 探测确认）→ 该任务整文件重传，UI 如实标注「此电视不支持续传，将重新上传」。
- 远端 `SIZE` > 本地大小（上次传了一半换了大文件同名）→ 自动改名重传，不覆盖不报错。

### 7.3 大文件与 U 盘物理限制

- >4GB 提示 FAT32 风险（FTP 层看不到文件系统，只能按经验提示）；
- 目标目录写一个极小探测文件确认可写 + 估算剩余空间（`LIST` 累计大小做粗估，拿不到就跳过，不阻塞）。

### 7.4 信任与安全

- 明文 FTP 是既有限制：首次连接时一行小字说明「传输在同一家庭 Wi-Fi 内进行」；
- 不上传任何遥测；队列与映射库只存本机。

### 7.5 删除：直删 + 强确认 + 删除前先下载兜底（2026-11-19 校准：软删除废弃）

产品决策改为直删（不再软删除/回收站/撤销）。FTP `DELE` 物理不可逆，安全靠三层：

1. **强确认浮层**：删除前 sheet 展示「已选 N 项 · 共 X GB」+ 缩略图条 +「永久删除，无法撤销」；DELE 不支持 → 删除入口禁用（「这台电视不支持删除」）。
2. **删除前先下载到本地**：可选勾选（设置页有默认开关），先把所选项取回本地再执行 DELE；取回登记持久化，取回全部成功后自动继续删除；取回未全成功则暂停删除并提示，重试取回成功后自动续删。
3. **失败 fail-safe**：DELE 无关键词响应映射 ioError（文件可能还在）而非 remoteNotFound，避免补删误计「已删」；未删全的批次保留登记待重试，不谎报完成。

历史兼容：旧版本软删除残留的 `.MITV-Trash` 目录 / `.MITV-Trash--` 前缀文件仅由浏览过滤（`BrowseFilter`）隐藏，不再新写、无还原/清空入口（残留清理策略 V1.1 再评估）。

**未实测**：真机 DELE/RNTO 响应文本谱待回归（本地 pyftpdlib E2E 与单测已覆盖映射规约）。

## 8. 技术架构（V1）

### 8.1 总览

```
┌────────────────────────── MiTV Helper.app ──────────────────────────┐
│  UI 层（SwiftUI）                                                    │
│   MainQueueView / OnboardingView / TVBrowserView / SettingsView      │
│──────────────────────────────────────────────────────────────────────│
│  应用服务层                                                           │
│   PickService      PHPicker 封装 + NSOpenPanel + 拖放接收             │
│   QueueService     队列状态机（等待/传输/暂停/失败/完成）+ 持久化      │
│   DiscoveryService 地址解析 + 局域网端口扫描 + 心跳                    │
│   NameCodec(Core)  GBK 原名保留 + 风险字符替换 + 同名去重（映射库未采纳） │
│   StagingStore     照片原图导出缓存（Application Support）             │
│   TVFileService    U 盘浏览列表/缩略图缓存 + 多选删除 + 删除前先下载编排   │
│──────────────────────────────────────────────────────────────────────│
│  传输层（TransferEngine 协议，可替换实现）                              │
│   ┌ CurlEngine（V1）：Process 调 /usr/bin/curl                        │
│   │   STOR 上传 -C - 续传、RETR 下载、LIST、RNFR/RNTO、DELE、SIZE      │
│   └ SwiftFTPEngine（V1.5 备选）：自研控制/数据连接，REST/APPE 精细控制  │
└──────────────────────────────────────────────────────────────────────┘
```

### 8.2 传输引擎选型对比（结论：V1 用 curl，接口留后路）

| 方案 | 优点 | 缺点 | 判断 |
|---|---|---|---|
| **子进程 curl**（本机已验证支持 FTP） | 被动模式/重连/`-C -` 续传久经考验；2-3 天可跑通全功能 | 进程管理、进度靠解析 stderr | **V1 采用**，封装成 `TransferEngine` 协议 |
| 自研 Swift FTP 客户端 | 进度/取消/REST 语义完全掌控，无进程开销 | 需处理被动模式、服务器方言，约 1-2 周 | V1.5 视稳定性切换 |
| SPM 社区库（如 SwiftFTPClient） | 省事 | 维护度一般、能力面窄 | 仅作参考 |

### 8.3 关键实现要点

- **照片导出**：PHPicker 的临时 URL 立即拷入 staging（`loadFileRepresentation` 的文件用后即焚）；HEIC 原图直传（电视端可播，常见小米电视支持 HEIC 解码；设置里留「转为 JPEG」开关兜底，AVFoundation 一行转换）。
- **队列持久化**：SQLite（队列 + 命名映射 + 历史），原子写。
- **并发**：默认 2 路并行（电视端是小服务器，不宜更多）。
- **心跳**：每 10s `NOOP`；两连失败 → 判掉线，进重连流程。
- **能力探测**（首次连接 + 设置里可重跑）：UTF-8 文件名 / REST / APPE / MKD / RNFR+RNTO（跨目录改名）/ DELE / MLSD / 匿名登录，结果缓存为「电视能力矩阵」，直接驱动 §7 的策略分支（命名、续传方式、删除直删或禁用）。

### 8.4 开发环境前置

当前机器仅有 CLT（Swift 5.1）→ **需安装 Xcode 14/15**（macOS 13.7 可装 Xcode 15.2）。无需其他第三方依赖（curl 为系统自带，SQLite 系统自带）。

## 9. 风险与未决问题

| # | 风险 | 影响 | 对策 |
|---|---|---|---|
| 1 | 电视 FTP 不支持 REST/APPE | 断点续传降级 | M0 实测定案；降级为整文件重传并如实告知 |
| 2 | 中文文件名行为因机型/固件而异 | 乱码/失败 | 首连探测自动分支，不赌运气 |
| 3 | 远程管理弹窗关闭即服务停止 | 频繁「假死」 | 心跳+自动重连+温和黄条提示，永不弹错误框 |
| 4 | 电视 IP 漂移 | 找不到电视 | 记住上次地址 + 自动重扫 + 向导可随时重跑 |
| 5 | FAT32 4GB / U 盘满 | 大文件传到最后失败 | 事前预警（4GB）+ 事中检测写入失败即时暂停整队 |
| 6 | 无 Bonjour，自动发现靠端口扫描 | 扫不到/扫到别的设备 | 扫描是辅助，手输地址是主路径 |
| 7 | HEIC 兼容性 | 个别老机型不显示 | 设置里「照片转为 JPEG」开关 |
| 8 | 服务器不支持 DELE | 删除不可用 | 首连探测；删除入口禁用 + 提示；「删除前先下载」作为有价值文件的事前兜底 |

**未决（需要你拍板或真机实测）：** ① 真机 DELE/RNTO 响应文本谱（能力矩阵其余项已实测）；② 产品名；③ 旧版回收站残留清理策略（现仅浏览过滤，V1.1 再评估）。
