### 新增发现

#### ⚠️ 现场缺陷（用户复现：下载正常 → 上传回 /Movies 后远端不能播放）【✅ 已修复】
> **修复（2026-11-19 下午）**：① 首传强制整传 STOR——`beginUpload` 改传 `resumeOverride: false`，仅同任务续传（重试/暂停恢复/重启恢复）走 APPE（`QueueService.swift`）；② 上传后 SIZE 复核——远端字节数 ≠ 本地即判失败并尽力删除坏文件，与下载侧校验对称（`SwiftFTPEngine.upload`）；③ D0 降级路径此前已在 b81bc4c 修掉（size() 探测 + 指纹后缀 + 禁 APPE）。测试 263 项全绿，含「首传 resume=false / 续传 resume=true」契约断言。
- **根因（结构性，仍在当前代码）**：`Sources/MiTVApp/QueueService.swift`（`startUpload` 约 487 行）对**每一次上传**都传 `resume: caps.appeResume == true`；`Sources/MiTVEngine/SwiftFTPEngine.swift:106-114` + `Sources/MiTVEngine/TransferPlanner.swift:8-13` 的语义是：**目标路径已存在同名文件且 `0 < 远端大小 ≤ 本地大小` 时，不整传，而是从远端大小处 APPE 追加**。
  ```swift
  // TransferPlanner.swift —— 对「任何」同名文件生效，不区分是不是本任务的断点
  guard localSize > 0, remoteSize > 0, remoteSize <= localSize else { return nil }
  return remoteSize   // → APPE 追加
  ```
  三种结局全部与症状吻合：
  1. 同名旧文件**更小** → APPE 把本地的后半段接到旧文件后半 → **「旧文件头 + 新文件尾」拼接坏文件**，226 照样返回、队列显示成功 → **不能播放**；
  2. 同名旧文件**同大小** → APPE 0 字节后直接报成功（`SwiftFTPEngine.swift:141-146` seek 到 EOF 空转一圈）→ 远端原封不动（内容还是旧的/错的）；
  3. 同名旧文件更大 → 整传覆盖（这个反而是好的）。
  APPE 续传本来只该用于**同一任务的断点续传**（远端半截文件是本次本地文件的真前缀）；引擎无法区分「我的断点」和「别人的同名文件」，而队列层把 resume 开关对所有上传一律打开。
- **同名是怎么漏进来的（三个入口）**：
  1. **大小写碰撞（今天 09:46 已修）**：FAT U 盘大小写不敏感，`IMG_0001.MP4` 与 `IMG_0001.mp4` 是同一文件；09:46 前 clash/uniqued 都是大小写敏感 → 判无冲突 → 目标名撞上现存文件 → APPE 拼接。**916e17b 提交信息原话：「IMG_1.MP4 vs IMG_1.mp4 此前会被判无冲突 → STOR 覆盖」——注意实际不是干净覆盖，而是 APPE 拼接/空转假成功**。相机文件普遍是 .MP4 大写，用户测试极易踩中。
  2. **uniqued guard 反向窗口（今天 09:46 已修）**：04:25–09:46 之间 guard 写反（占用→原样返回/未占用→顺延），名字被占用时反而原样返回 → 直接撞名。
  3. **列表失败降级（未提交 D0，仍开放）**：`startUploadWithFallback` 原名直传、无顺延，LIST 一抖就撞名。
  另外：**此前失败/中断留下的同名半截文件**（测试过程中必然产生过）+ 后续任意同名上传 = 同样触发 APPE 拼接，连大小写洞都不需要。
- **第二处独立缺陷（放大器）**：上传成功路径**没有远端 SIZE 复核**。下载有 `received != total` 校验并清半截文件（`SwiftFTPEngine.swift:240-255`），上传只信服务器的 226（`SwiftFTPEngine.swift:157-158`）。服务器侧静默截断（FAT32 单文件 4GB 上限、磁盘满、嵌入式服务器怪癖）会**报成功但文件是截断的** → 同样不能播放。
- **为什么「本地能播、远端不能播」**：本地文件是好的（下载链路校验完整）；上传要么把它拼接到旧文件上（拼接坏文件），要么写成功但被服务端截断，要么 0 字节假成功留旧内容。三种情况用户看到的都是「上传完成」。
- **自查方法（区分是哪种）**：`mitvctl download` 把远端文件拉回来 `cmp`/看大小——远端**大小变小/变了**=拼接或截断；远端**大小相同但内容不同**=0 字节假成功；本地扩展名是 `.MP4` 大写或 /Movies 里本来有同名文件/上次测试的残留半截 → 命中名字碰撞入口。文件 ≥4GB 则重点怀疑 FAT32 截断。
- **修复建议（按优先级）**：
  1. **新任务首传强制 `resume: false`（整传 STOR）**；只有「同一任务失败/暂停后的续传」（远端半截确为本文件前缀）才允许 APPE。最简实现：`QueueItem` 记 `hasParticipatedUpload`，`startUpload` 据此传 resume；或引擎把 APPE 限定为显式 `resumeOfPartial` 标志。
  2. **上传成功后复核 SIZE**（capabilities.sizeCommand 时 `remoteSize == localSize` 才算成功，否则报失败并清理/提示），与下载对称。一条 SIZE 命令的成本。
  3. D0 降级必须顺延命名（见 D0 条）；可选：APPE 续传前用 `downloadPrefix` 校验远端前缀确为本地文件前缀。


#### D0（新·数据安全）· 列表失败降级直传绕过重名判定，且在 APPE 续传下不止是「覆盖」
- **位置**：未提交改动 `Sources/MiTVApp/QueueService.swift`（`chooseUploadDir`/`finalizeUploadRouting` 失败分支 + 新增 `startUploadWithFallback`，约 313-320、342-349、447-456 行）
- **描述**：`list("/")` 或目标目录 `list` 失败时，不再失败（旧注释原话是「宁可失败也不覆盖」），而是降级为「原名直传」，**完全跳过**尺寸/指纹同名判定与顺延命名。新注释自认「覆盖风险让位于可用性」，但实际风险比覆盖更重——目标是空盘 LIST 怪癖场景（此时无同名文件，确实安全），可一旦 LIST 是**偶发失败**且目录里恰有同名旧文件：
  1. 旧文件**更大** → 整传 STOR 覆盖（丢旧文件）；
  2. 旧文件**更小** → `SwiftFTPEngine.upload` 的 SIZE+APPE 续传会从旧文件大小处**追加**，产出「旧文件头 + 新文件尾」的混合坏文件（`TransferPlanner.resumeOffset` 对 `remoteSize<=localSize` 一律走 APPE）；
  3. 旧文件**同大小** → APPE 0 字节直接报成功，用户以为传了新片，电视上还是旧内容。
- **真实场景**：重传一个改过内容但同名的家庭视频（很常见：剪辑后重新导出覆盖旧版）→ 该刻 TV 的 LIST 恰好抖一下 → 旧视频被毁/被拼接/被冒充成功。并发两项同名时 `inflight` 互斥也一并跳过，双双直传同一路径。
- **建议**：降级前先 `engine.size(remotePath)`（LIST 失败时 SIZE 常常仍可用，只多一条命令）：不存在 → 原名直传（保住空盘可用性）；存在 → 走 `原名-md5前8` 或 `原名 (N)` 顺延（保住不覆盖）。至少对 `resume` 关闭降级路径的 APPE（降级时改整传 STOR 并目标名做后缀），避免拼接坏文件。新增测试 `testEmptyDiskFallback` 只覆盖了「列表失败仍能传」，建议补「列表失败 + 远端已有同名」用例。

#### 顺带观察（非缺陷）
- **BrowseFilter**（`Sources/MiTVApp/BrowseFilter.swift`，新增）：隐藏规则从「仅 .MITV-Trash*」扩大为**全部点开头文件** + 系统目录（System Volume Information 等）。产品有意为之（commit 9cc36f8「对普通用户只显示自己的内容」），注意用户自己放在 U 盘的 `.xxx` 文件也将不可见、不可删；FOUND.%d 规则实现正确。

## 一、阻断用户主路径

### B1. 拖放文件夹不会展开，整夹拖入被静默忽略【✅ 已修复，见文首复审更新】
- **位置**：`Sources/MiTVApp/AppCoordinator.swift:434`（拖放/Dock 入口），对照 `Sources/MiTVApp/PickService.swift:36`（面板入口）
- **描述**：文件选择面板会把文件夹递归展开（`files.append(contentsOf: PickService.expandFolder(url))`），但拖放与 Dock 入口的 `enqueueFileURLs` 只做 `PickService.filterMedia(urls)`，没有展开。文件夹名通常无媒体扩展名 → `MediaKind.of` 返回 `.other` → 全部被过滤。
- **代码证据**：
  ```swift
  // AppCoordinator.swift:434（拖放路径）
  let result = PickService.filterMedia(urls)
  guard !result.media.isEmpty else { showToast("这些文件不是照片或视频"); return }
  ```
- **真实场景**：用户把「2026 春游」整个文件夹拖进窗口（或拖到 Dock 图标）→ 只弹「这些文件不是照片或视频」/「已忽略 N 个不支持的项目」，一项都不入队。同一文件夹用「从文件夹挑选」却正常。若文件夹名恰好带媒体扩展名（如 `mv.mp4/`），还会穿透过滤、在上传时报「本地文件不存在」。
- **建议**：在 `enqueueFileURLs` 里对目录 URL 调用 `PickService.expandFolder` 再 `filterMedia`（与面板路径合并为同一入口）。

### B2. 目录形态回收站启用后，非根目录文件的软删除全部失败
- **位置**：`Sources/MiTVApp/TVFileService.swift:143,189-190`、`Sources/MiTVApp/SoftDeletePolicy.swift:49-54`
- **描述**：目录形态目标路径为 `/.MITV-Trash/<扁平化父目录>/<原名>`（如 `/Movies/a.mp4` → `/.MITV-Trash/Movies/a.mp4`），但整条链路只创建 `/.MITV-Trash` 根（`TVFileService.swift:143` 唯一一次 MKD），从未创建 `/.MITV-Trash/Movies` 这类子目录。RNTO 到不存在的父目录必然 550。单元测试只断言了路径字符串（`ServiceTests_B.swift:177-182`），没有验证 move 成功。
- **代码证据**：
  ```swift
  // TVFileService.swift:143 —— 全流程唯一的建目录
  engine.makeDirectory(endpoint, path: SoftDeletePolicy.trashRoot) { _ in ... }
  // SoftDeletePolicy.swift:51-53
  return trashRoot + "/" + parent + "/" + name   // 父目录从不存在
  ```
- **触发条件**（满足其一即走目录形态）：`caps.mkdir == true`，或电视上 `/.MITV-Trash` 已存在（`TVFileService.swift:146,151` 的 `checkTrashDir`）。目标电视 MKD=550 且首次删除走前缀形态（可用）；但一旦回收站目录存在（手动建过、别的工具建过、MKD 可用的机型），删除 `/Movies/…`、`/Pictures/…` 下任何文件都会失败并报「N 项没有成功」。根目录文件（`/.MITV-Trash/<名>`）不受影响。
- **建议**：move 之前对 `flattenParent` 逐级 MKD（或改用 `/.MITV-Trash--…` 平铺命名），并把「目录形态 move 成功」纳入测试。

## 二、功能缺陷

### D1. 照片选择器导出丢弃原文件名，电视上得到 export-0.heic 一类名字
- **位置**：`Sources/MiTVApp/PhotoPickerView.swift:255`（配合 `StagingStore.swift:19-30`）
- **描述**：导出临时文件命名为 `export-\(i).\(ext)`，`originalFilename` 只用于取扩展名；`StagingStore.stage` 以 `lastPathComponent` 落入暂存区，`QueueService.addUploads` 以其为 `displayName`，最终成为远端文件名。与设计文档「原名尽可能保留」（`docs/PRODUCT_DESIGN.md` §7.1、`docs/ARCHITECTURE.md:126`）相悖。
- **代码证据**：
  ```swift
  // PhotoPickerView.swift:255
  let tmpFile = tmpDir.appendingPathComponent("export-\(i).\(ext)")
  // :291 原名只用于取扩展名
  let original = resource.originalFilename
  ```
- **真实场景**：用户从照片库挑 10 张照片发送 → 电视上出现 `export-0.heic … export-9.heic`；再发一批变成 `export-0 (2).heic`（暂存区顺延命名）。电视上完全无法按名字辨认照片。附带问题：每批导出把原图完整拷入 `Staging/` 且永不清理，大视频批量导出会持续占用本地磁盘。
- **建议**：导出文件直接用 `resource.originalFilename`（经 `StagingStore.uniquedURL` 顺延），并给 Staging 增加「任务完成后清理」策略。

### D2. toast「撤销」后不刷新电视浏览器网格，撤销看起来无效
- **位置**：`Sources/MiTVApp/AppCoordinator.swift:602-608`；`TVBrowserView.swift:143-146`（`reloadIfNeeded` 只载一次）
- **描述**：撤销闭包只调 `files.restore` 并弹 toast，没有任何 `reload()`。删除完成时 `after()` 已经 `reload()` 过（网格里文件已消失），撤销把文件移回电视后网格仍缺该文件；且再次点「电视」导航走 `reloadIfNeeded` 不刷新，必须进出子目录才能看到。
- **代码证据**：
  ```swift
  // AppCoordinator.swift:602-608
  self.showToast(text, undo: { [weak self] in
      self?.files.restore(outcome.records, ...) { restored, failed in
          if restored > 0 { self?.showToast("已还原 \(restored) 项") }  // 无 reload
      }
  })
  ```
- **真实场景**：删错文件 → 点「撤销」→ 提示「已还原 1 项」但列表里文件没有回来 → 用户认为撤销失败，可能重复删除/重复还原。
- **建议**：restore 完成回调里（主队列）刷新浏览器（`browserView.reload()` 或等价的「标记脏 + 下次进入刷新」）。

### D3. 清空回收站后残留幽灵列表，再次「还原」误报失败
- **位置**：`Sources/MiTVApp/TVBrowserView.swift:178-181, 353-360`
- **描述**：`restoreSelected` 完成后调 `enterTrash()`；当全部记录被还原后 `trashStore.count == 0`，`enterTrash` 在 guard 处 toast「回收站是空的」并直接 return，**不清理 `trashRecords`/不 `reloadData`**。网格仍显示已还原的项目；再点「还原」对已不存在的 trashPath 发起 move → 「有 N 项还原失败」。
- **代码证据**：
  ```swift
  // TVBrowserView.swift:178-181
  private func enterTrash() {
      guard coordinator.trashStore.count > 0 else {
          coordinator.showToast("回收站是空的")
          return          // ← 视图状态未更新
      }
  ```
- **真实场景**：回收站里删了 3 个文件 → 全选 → 还原 → 提示成功但列表还在 → 再点还原报失败。主撤销备份路径体验崩坏（数据本身不损坏，记录已从 store 移除）。
- **建议**：`enterTrash` 的空分支也应清空 `trashRecords`、`reloadData`、`refreshChrome`（或还原后统一 `reload()` 回正常浏览态）。

### D4. 删除确认浮层弹出期间，⌫/Esc 仍被浏览器快捷键拦截
- **位置**：`Sources/MiTVApp/TVBrowserView.swift:451-467`（本地键盘监视），`AppCoordinator.swift:564`（ConfirmOverlay 挂在 `rootDrop`，与浏览器同窗口）
- **描述**：监视器的豁免条件只排除了 sheet（别的 window）和文本输入，ConfirmOverlay 是同窗口普通子视图，拦截照常生效。⌫ 会再次走 `deleteSelected` → 叠出第二个确认浮层；Esc 被 `return nil` 吞掉，既不关对话框，还顺带清掉了背后的选中项。
- **代码证据**：
  ```swift
  // TVBrowserView.swift:451-455
  event.window === self.window,   // ConfirmOverlay 同 window，条件通过
  ...
  if event.keyCode == 53 { self.clearSelection(); return nil }   // Esc 被吞

  ```
- **真实场景**：弹出「移到电视回收站？」后习惯性按 Esc 想取消 → 对话框不动、选择被清空；按 ⌫ → 叠加两个确认框，都点确认后第二次删除报「N 项没有成功」。
- **建议**：监视器加「确认浮层/向导可见时不拦截」守卫（如 `confirmOverlay?.window == nil || confirmOverlay?.superview == nil` 判断），并让 Esc 关闭最上层浮层。

### D5. 慢网络下，在途目录列表回调会冲掉回收站视图
- **位置**：`Sources/MiTVApp/TVBrowserView.swift:153-165`（`reload` 回调无 `isTrashMode` 判断）vs `:177-191`（`enterTrash`）
- **描述**：`reload()` 的 `files.list` 回调无条件写 `entries`、**清空 `trashRecords`** 并 `reloadData`。用户在列表返回前点了「回收站」，晚到的回调会把回收站冲成 0 条并显示「这个文件夹是空的」。
- **代码证据**：
  ```swift
  // TVBrowserView.swift:161-165（list 回调内）
  self.entries = visible
  self.trashRecords = []     // ← 即使用户此刻已在回收站视图
  ```
- **真实场景**：删完文件 `after()` 触发 `reload()`（电视响应慢）→ 用户马上点「回收站」想撤销 → 回收站显示为空，需点返回再进才能恢复。
- **建议**：列表回调入口处 `guard !isTrashMode`（或用请求序号丢弃过期回调）；同类问题也适用于连续两次 `reload()` 交叉。

### D6. 跨批次下载重名会互相覆盖，甚至写花同一个本地文件
- **位置**：`Sources/MiTVApp/QueueService.swift:128-143`（重名判定只在入队时、按批次隔离），`Sources/MiTVEngine/SwiftFTPEngine.swift:198`（下载截断式写入）
- **描述**：`addDownloads` 的 `usedNames` 只覆盖当次调用，磁盘 `fileExists` 检查也只在入队瞬间做。两批下载目标目录相同（面板记住上次目录）且文件名相同时，若第一批还没开始写盘，两批都会拿到同一 localPath；下载是 `truncateFile(atOffset: 0)` 覆盖式，后者毁掉前者（并发 2 时还可能交错写花）。
- **代码证据**：
  ```swift
  // QueueService.swift:128 —— 仅本批次
  var usedNames = Set<String>()
  // SwiftFTPEngine.swift:198
  fh.truncateFile(atOffset: 0) // 覆盖式下载
  ```
- **真实场景**：从 `/a/IMG_0001.jpg` 和 `/b/IMG_0001.jpg` 先后点「下载」都存到 ~/Downloads，第一批还在排队时入第二批 → 本地只剩一个 `IMG_0001.jpg`（且内容可能损坏）。
- **建议**：把「已占用的本地目标名」登记为队列级集合（入队即占位，终态失败再释放），或入队前扫描所有未终结下载项的 localPath。

### D7. 缩略图缓存文件名超长，中文长路径图片缩略图永不显示
- **位置**：`Sources/MiTVApp/TVFileService.swift:308`
- **描述**：缓存文件名是整条远端路径的 percent-encoding（含 `/`，每个中文字变 9 个 ASCII 字符），塞进**单个**文件名。超过 macOS NAME_MAX=255 字节后 `createFile` 失败 → 永远走图标兜底；且失败不记忆（无负缓存），每次 `reloadData` 又发起一次完整 RETR。
- **代码证据**：
  ```swift
  // TVFileService.swift:308
  let localURL = thumbDir.appendingPathComponent(
      entry.path.addingPercentEncoding(withAllowedCharacters: .alphanumerics) ?? ...)
  ```
- **真实场景**：电视上有 `/Pictures/2024年家庭旅行照片精选/海边的夕阳与孩子们 IMG_2043.jpg` 这类中文长路径（本产品目标用户几乎必然遇到）→ 图片永远显示默认图标，且每次浏览都白白重下一遍。
- **建议**：缓存文件名改用路径哈希（如 md5(path) + 扩展名），并给失败加负缓存。

### D8. 「全部暂停」期间断线重连后，「全部继续」按钮失效
- **位置**：`Sources/MiTVApp/QueueService.swift:168-213`（`resumeAllByUser` 的 `guard hold == .user` 在 181 行）
- **描述**：`pauseAllByUser` 置 `hold = .user`；随后 `autoPauseForDisconnect` 把 hold 覆盖为 `.disconnected`（196 行），重连后 `autoResumeAfterReconnect` 清成 `.none`。此时用户点「全部继续」→ `guard hold == .user` 不满足 → 静默 no-op，用户暂停的任务永远停着（单项「继续」按钮仍可用）。
- **代码证据**：
  ```swift
  // QueueService.swift:181
  func resumeAllByUser() {
      guard hold == .user else { return }   // 断线流程已把 hold 改掉 → 死按钮
  ```
- **真实场景**：网络不稳时用户「全部暂停」→ 黄条提示断线又重连（这正是会点全部暂停的场景）→ 点「全部继续」没反应，只能一项一项恢复。
- **建议**：把用户暂停意图与断线 hold 拆成两个独立标志（或 `resumeAllByUser` 在 hold==.none 时也恢复 `autoPaused==false` 的暂停项）。

### D9. `utf8Filenames` 探测结果从未被使用，命令始终按 GBK 发送
- **位置**：`Sources/MiTVEngine/SwiftFTPEngine.swift:32`（`withConnection` 恒用默认 `Config`，encoding=GBK）；探测仅在自己的连接上切 UTF-8（`CapabilityProbe.swift:156`）
- **描述**：文档承诺「探测 utf8Filenames 通过才切 UTF-8」（`SwiftFTPEngine.swift:6`、`ARCHITECTURE.md:47`），但 `caps.utf8Filenames` 除存入 `tv.json` 外没有任何消费方；每个操作都新建连接并用 GBK 编码路径。对目标电视（GBK）无影响；对 UTF-8 文件名的电视/固件，中文名会乱码、删除/下载寻址错字节。
- **建议**：`SwiftFTPEngine` 各入口读取 `capabilitiesProvider`（或在 endpoint 侧带 capabilities），utf8Filenames==true 时 `Config.encoding = .utf8`。目标机型不影响发布，可排后。

## 四、存疑待确认（证据不足以断言为缺陷）

### S1. 前缀回收站名对含 `--` 的名字存在歧义
- **位置**：`Sources/MiTVApp/SoftDeletePolicy.swift:42-46,57-62`
- **说明**：`/报告/最终版.mp4` 与根目录文件 `/报告--最终版.mp4` 会得到同一个回收站名 `.MITV-Trash--报告--最终版.mp4`。若服务器 RNTO 到已存在目标会覆盖（SwiFTP 语义未实测），可能出现撤销还原错内容。概率低（需名字含 `--`），但最坏结果是内容对调。**建议**：命名规约里对 `--` 做转义，或补一条 RNTO 覆盖语义实测。

### S2. 批量完成通知被 `notifyChange` 合并节流吞掉的设计脆弱性
- **位置**：`Sources/MiTVApp/QueueService.swift:570-578`（`guard !notifyPending else { return }` 连同批量判定一起跳过）
- **说明**：引擎契约「结束时必有一次最终进度」——若最终进度回调与完成回调背靠背到达（Mock 引擎与测试桩确定如此），完成事件的 `notifyChange` 被合并跳过，`onBatchCompleted`（完成 toast/声音/系统通知、「删除前先下载」的后续删除）就丢失或延迟到下一次队列活动。**真实引擎路径上 `withConnection` 的 `conn.quit()` 往返（毫秒级）恰好把两个回调拉开，通常能躲开**——因此不认定为现实缺陷，但批量判定藏在合并守卫后面属结构性脆弱，`download-first` 删除链路一旦踩中会「延迟很久后突然执行删除」。**建议**：批量完成判定移出合并守卫（每次 `applyEngineEvent` 终态迁移后无条件检查）。

### S3. `bestResource` 的 `resources.first!` 理论上可空数组崩溃
- **位置**：`Sources/MiTVApp/PhotoPickerView.swift:283-288`
- **说明**：`PHAssetResource.assetResources(for:)` 在个别资产状态（同步中/iCloud 异常）可能返回空数组，触发强制解包崩溃。实际概率很低，未能构造真实触发路径。**建议**：改成 `resources.first ?? 失败计入 failed`。

## 六、总体评价

> **复审后修正**：B1 已修复（拖文件夹通路打通）；但未提交的「列表失败降级直传」（D0）把此前「不覆盖远端」的安全属性换成了可用性，且在 APPE 续传下有拼接坏文件的更重风险——**建议先落 D0 的 size() 探测方案再提交该改动**。其余结论不变。
>
> **现场缺陷（最高优先）**：用户实测复现「下载正常、上传回 /Movies 远端不能播放」。根因是**每次上传都开 APPE 续传语义**（同名旧文件会被拼接/假成功）+ **上传后无 SIZE 复核**（截断静默通过）。名字碰撞的三个入口中两个今天已修（大小写、guard 反向），但 APPE 语义本身和缺失的复核仍在当前代码。**建议修复顺序更新：现场缺陷 ①（首传禁 APPE + SIZE 复核）> D2/D3 ≈ D0 > D1 > B2 > D4 > 其余。**

**核心旅程（连接 → 选照片 → 发送到电视 → 电视上可看）可用**，传输内核（GBK 名、续传、重名判定、断线恢复、重启续传）质量扎实，测试与 e2e 有覆盖。

**薄弱区集中在「删除/撤销」与「入口一致性」**：
1. 拖文件夹完全无效（B1）与照片导出丢原名（D1）是发送侧最影响观感的两处，恰好都在用户最先走到的路径上；
2. 删除/撤销三处（B2/D2/D3）让用户在「删错了想恢复」这个安全关键时刻得到错误反馈——撤销实际有效却看起来失败（D2）、清空回收站后幽灵列表（D3）、特定条件下删除整批失败（B2）；
3. 其余为边界体验与条件性问题（D4-D9、E1-E3），不阻断发送主链路。

**建议修复优先级**：D2/D3（撤销可见性）≈ B1（拖文件夹）> D1（原名）> B2（目录形态删除）> D4 > D6/D7/D8 > 其余。
